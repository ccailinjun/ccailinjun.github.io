一、.vscode/tasks.json 是什么

它是 VS Code 的任务声明文件（不是 CMake 的一部分），作用是把一串 shell 命令包装成可在 Cmd+Shift+P → Tasks: Run Task 或 Cmd+Shift+B 里一键执行的操作。它本身不编译任何东西，真正的编译由它调用的 cmake 完成。

1.1 顶层字段

  • version: "2.0.0" —— tasks.json 的 schema 版本（注意：与 CmakePresets.json 里的 "version": 3 是两个完全不相干的东西）。
  • tasks[] —— 五个任务，下面逐个拆。

1.2 各字段通用含义

字段 含义
label 任务名，被 launch.json 的 preLaunchTask 引用
type: "shell" 交给系统 shell（zsh）执行
command / args 实际命令行
options.cwd 工作目录，这里统一是 ${workspaceFolder}
group.kind: "build" + isDefault: true 绑定到 Cmd+Shift+B
problemMatcher 把终端输出解析成”问题”面板条目，支持点击跳转
isBackground 长驻进程，配合 beginsPattern/endsPattern 判断启动完成

1.4 任务 ②：Build (Debug)（build 组默认，Cmd+Shift+B）

这是唯一真正产出可执行文件的任务。它把构建完全委托给 CMake + Ninja，--preset arm-gcc-debug 从 CmakePresets.json 取参数。

二、可执行文件是怎么生成的

tasks.json 只是”按钮”，真正的流水线是 CMake Presets → 交叉编译 → 链接 → 后处理。分 5 个阶段。

阶段 0：配置（configure）

CmakePresets.json 定义了两个预设：

  • generator: Ninja → 增量编译靠 Ninja。
  • binaryDir: build/debug → 所有产物落在这里（实测目录里确实有 ble_hzpc.elf/.bin/.hex/.lst/.map）。
  • CMAKE_TRY_COMPILE_TARGET_TYPE: STATIC_LIBRARY → 让 CMake 的编译器探测只编译不链接（裸机没有可用的链接测试目标）。

三、整体流程图

四、几个值得注意的点

  1. 没有 configure 任务。tasks.json 里只有 --build，首次克隆或改了 CMakeLists.txt 结构后需手动跑一次 cmake --preset arm-gcc-debug（或靠 CMake Tools 扩展）。实测 build/debug/ 里已有 CMakeCache.txt 和 build.ninja，说明已配置过。

  2. 预设文件名大小写：工程里叫 CmakePresets.json，而 CMake / VS Code CMake Tools 按惯例查找 CMakePresets.json。macOS 默认分区大小写不敏感所以能work，但换到大小写敏感的环境（或 Linux CI）会找不到预设。

  3. arm-gcc-release 预设没人用：只有 debug 被三个任务引用，release 目前是”定义了但没接按钮”。

  4. Flash 任务假设 build/debug/ 已存在：命令直接往 ${workspaceFolder}/build/debug/flash.jlink 重定向，若目录没建会失败（当前目录已存在，所以没问题）。

  5. build/ 根目录有一批旧产物（ble_hzpc.elf/.bin/.hex/.lst/.map），是早前 binaryDir 直接设为 build 时留下的，与现在的 build/debug 无关，容易混淆。

  6. 332K 上限的三处联动：CMakeLists.txt 的 FLASHENV_OFFSET、Inc/fal_cfg.h 的 FAL_PART_TABLE 偏移、common/ota/ota.c 的 OTA B 槽保底值，改一处必须同步另外两处，否则会静默覆盖参数区。

  7. gcc/Makefile 是历史遗留路径，CMake 才是当前主用；两者源列表已不完全一致，维护时以 CMakeLists.txt 为准。
